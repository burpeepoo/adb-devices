# Scout 重构能力契约

最后更新：2026-07-15

## CAPABILITY

Scout 为 Android 工程师、QA 和支持人员提供一次可追溯的自动化功能走查或 Bug 复现：用户只需给出目标、可选包名、参考链接和项目目录，Scout 绑定当前设备，持续执行“观察 → 操作 → 验证”，直到功能路径完成、遇到必须由人完成的受保护边界，或确认执行失败；随后自动生成并关闭一份证据报告。

用户看到的是一个任务和一份报告，而不是 Agent 对话、采集记录、审批卡或设备性能面板。

## 当前问题

- 任务关闭事实分散在 Evidence Session 与 Agent 对话两个对象中，容易出现“Agent 已完成但任务仍不能重新开始”或“任务已结束但其实尚未操作”。
- 零个 UI 节点被错误当作页面事实或终点；屏保、启动器、无障碍窗口未就绪和无障碍服务失效没有统一恢复链路。
- UI 点击同时依赖模型旧坐标、最新层级和 Agent 节点点击，页面变化后会出现 `ui.tap` 与最新可点击节点不匹配。
- 自动任务仍沿用半自动审批和大量诊断上下文，模型会等待 ADB Manager 结果或把设备状态采集当成主要目标。
- 证据历史、Agent 对话和导出结果的删除/关闭边界不清晰。

## 用户场景

### 功能走查

用户输入“走查 Calendar 的新建、编辑、删除流程”，可选包名和参考链接。Scout 自动启动目标 App，退出屏保或启动器，逐步检查入口、控件可用性、状态变化、结果变化和恢复路径，并比较参考资料可见的 UI 差异。未提供参考链接时，继续做功能走查，只把 UI 对比标记为证据缺口。

### Bug 复现

用户输入复现步骤、目标包名和预期现象。Scout 自动执行可逆步骤，围绕异常前后采集 UI、截图、前台窗口和必要的 Logcat；只有在确实观察到崩溃、ANR、卡顿或资源相关症状时才升级性能诊断。

### 设备处于屏保或无节点

零节点不是完成条件。Scout 先读取前台窗口和截图，尝试唤醒/返回，再启动明确指定的目标包；没有包名时，只在目标与唯一可启动 App 匹配时自动选择。每一步都必须重新检查前台和 UI。恢复仍失败时，报告“恢复失败”及证据，而不是报告“已完成”。

### 需要人完成的受保护动作

普通导航、滑动、返回、普通确认、提交和继续直接执行。登录、退出登录、授权/权限授予、支付/购买、清除数据、卸载、重置、重启和等价操作不展示审批卡；Scout 先继续其他可行覆盖，最终报告明确写出边界、唯一需要用户做的动作和重新开始方式。

### 新建任务与历史任务

运行中只有一个 Scout Run。完成、阻塞、失败或用户停止后自动释放新任务入口。历史列表展示任务类型、目标和稳定状态列；删除关闭记录时，同时删除关联的本地对话记录，但不删除已导出的截图、报告或压缩包。

## IMPLEMENTATION CONTRACT

### 事实源与状态

新流程以一个 `EvidenceSession` 作为 Scout Run 的持久事实源；Agent 对话只是该 Run 的可选展示 transcript，不拥有任务状态。有效状态为：

`not_started → running → reporting → completed | blocked | failed | stopped`

`agent_completed` 不再作为可阻塞新任务的持久状态。终端结论一旦被验证，就必须进入 `reporting`，报告成功后关闭 Run。

### 运行循环

1. 检查当前设备身份、CLI 运行时和截图目录。
2. 创建唯一 Scout Run，并将目标、包名、参考链接、项目目录写入 Run 摘要。
3. 读取前台窗口、`ui.inspect` 和关键截图。
4. 对屏保、启动器、空节点或无障碍窗口执行有限恢复；恢复后重新读取证据。
5. 让 Agent 每轮只提出下一组有界工具调用；工具调用由桌面端执行，结果回传后才允许下一轮。
6. 每个 UI 动作都基于执行前的最新快照解析目标，动作后重新检查；解析不到目标时先刷新并做一次语义重定位，仍失败才记录动作失败。
7. 将功能覆盖、UI 差异、行为/实现差异、证据缺口和必要诊断写入报告。
8. 验证唯一终端结论，生成报告并自动关闭 Run。

### 默认证据

功能走查默认收集 UI 层级、关键截图、前台/窗口、包名和动作后的验证结果。Bug 复现额外在异常前后收集 Logcat。默认不收集设备摘要、内存、CPU、温度、电池、网络或 GPU 基线。

### 操作策略

- Scout Run 内不存在用户可见的权限级选择和审批卡。
- 安全、可逆的 UI 与 ADB 输入自动执行。
- 受保护动作返回结构化 `blocked` 结果，不执行，也不创建 approval message。
- 无障碍优先；无障碍不可用或层级为空时，可以使用一次新截图加安全的 `shell input keyevent/tap/swipe` 兜底，并必须复核结果。
- 原始错误、内部命令、长 JSON 和屏幕状态细节默认折叠在证据详情，不占据主任务流。

### 报告契约

报告必须包含：目标与范围、设备与包名、执行结论、功能覆盖、UI 差异、行为/实现差异、问题及严重度、证据缺口、必要诊断、建议下一步和证据文件索引。事实、用户输入和 Scout 推断必须分开标记。缺少参考资料只能标记为证据缺口，不得伪造对比结论。

### 空状态

- 未开始：只展示输入和开始按钮。
- 运行中：展示目标摘要、当前阶段、最近一步和停止按钮。
- 报告生成：保留任务摘要，显示报告生成状态，不允许重复启动。
- 已完成/已阻塞/已失败/已停止：展示结论、报告摘要、导出和删除历史。
- 无历史：展示简短空态，引导开始一次走查，不展示内部术语。

## NON-GOALS

- 不把 Scout 改造成设备性能监控器。
- 不在任务流程中保留半自动审批卡。
- 不让用户手工采集截图、备注或“关闭报告”；导出是唯一手动证据动作。
- 不在本次重构中替换 Agent CLI、模型供应商或 ADB 基础连接模块。
- 不宣称已看到不可访问的 Figma、飞书或本地参考资料。

## 验收标准

1. 目标 App 处于屏保、启动器或零节点时，走查不会直接结束；会有可验证的恢复尝试和结果。
2. 连续 `ui.inspect` 返回零节点时，任务最多进入一次受控恢复分支，随后继续、阻塞或失败，不能进入假完成。
3. 目标节点移动、文本节点不可点击或 Agent 无障碍点击失败时，动作会基于新快照重定位或降级到安全 ADB 输入，并明确记录置信度。
4. 自动走查过程中不产生审批卡，也不默认调用性能/内存采集。
5. 终端报告关闭任务，关闭后可以立即新建另一种任务。
6. 历史 Walkthrough 和 Bug Repro 均可删除，状态列宽度固定，不会被标题挤成竖排。
7. 报告内容可以独立回答“功能是否可用、UI 有什么差异、行为/实现有什么差异”，并带有可打开的本地证据路径。

## 交付顺序

先建立纯函数状态机、恢复策略和 UI 目标解析测试；再接入桌面任务执行器，移除自动任务的审批/性能默认分支；最后收口任务界面、历史删除和报告导出，并用真实 Tauri 设备走查验证。

## 未决事项

- 具体的目标 App 自动识别只允许“明确包名”或“目标与唯一可启动 App 匹配”，不做模糊多候选猜测。
- 受保护动作发生后是否继续其他路径，由当前 Run 的可达覆盖决定；若没有其他可达路径，终端结论为 `BLOCKED_NEEDS_HUMAN`。
- 参考链接读取是否可用取决于本机对应连接器；不可用时不阻塞设备侧功能走查。
